“有活人感”落实为口吻、回应方式、记忆边界和消息节奏，不要求伪装真人身份、编造现实经历或捏造已经完成的行动。短句是日常偏好，需要解释时允许完整表达；不要求所有回复必须有固定条数，也不要求每次都带表情或混合气泡。容量上限和发送节奏是可配置的资源保护参数，不是写作模板。

现有身份校验、工作消费租约和冷却仍是前提。`onebot.rs::require_bound_account` 在发送前验证绑定身份；`protocol/runtime/workers.rs`、CLI `commands/protocol/daemon.rs` 使用账号 `message-worker.lock`；`messaging/events.rs` 的冷却键包含账号、消息类型和目标。但是 GUI 接收消息后会并行启动生成任务，单消费租约不能防止同会话的多个生成结果或多条发送互相插入。

另有两处需要在接入时处理：消息先落库再组装历史，当前来信可能同时存在于历史和新输入中；`storage/tables/messages.rs::get_messages_by_target` 会按相近时间内的同内容删除消息，不能据此删除用户真实连续发送的相同短句。新链路使用事件 ID 和平台消息 ID 去重，历史组装明确排除本轮输入，而不是按文本猜测。

群聊身份目前也不能视为完整实现：`pipeline.rs::build_history` 将消息压为 `ChatMessage { role, content }`，多个群成员都变成同一 `user` 角色；`events.rs` 虽能读取 `user_id`、`sender.card`/`nickname` 和 `self_id`，当前传入回复生成的主要是正文与显示名，未形成稳定成员键、对话指向和引用来源链。新增设计须补全这些结构，不能仅在 prompt 中写“分清是谁”来替代。

## 第一版产品边界

第一版提供可配置的自然对话人设、权限内上下文、独立任务会话、`text`/基础 `face` 回复计划、审核与可靠投递，以及少量可解释的工具场景。所有入口共用账号、权限、任务和回执领域，GUI、CLI、MCP 不另写发送策略。

暂不包括任意 Shell、开放文件系统、浏览器自动操作、账号管理代理、自动加好友/拉群、任意外部写接口、商城 `mface`/自定义图片/语音/视频表情包。新方向不提前实施尚待讨论的登录保持或内存策略，不扩大 QQ 进程所有权，不把协议状态检查变成登录、推理或发送。

默认迁移保留现有规则与文本草稿，不自动启用更宽的接管范围、工具权限、主动消息或后台记忆。新格式可以读旧的单文本草稿；旧入口保留兼容文本返回，新契约通过明确版本和可选字段扩展，不把结构化计划直接作为 JSON 文本发给联系人。

## 固定作用域与任务独立会话

任务创建时由程序确定不可变作用域：`machineId + accountUin + targetType + targetId + taskId`。`targetType` 参与键，避免群号与好友号相同造成混淆。任务由用户动作或已授权规则创建，`taskId` 使用随机编号；每次模型调用另有 `runId` 和单调递增的运行序号。

| 对象 | 归属和持久证据 | 运行与恢复规则 |
| --- | --- | --- |
| `Task` | 账号 SQLite；固定目标、来源事件、发起方式、状态、任务版本、权限引用 | 任务不能随界面当前账号或当前联系人变化改绑；取消、完成、归档有明确状态 |
| `TaskSession` | `taskId`、供应方、模型目标、会话代次、历史版本及可选原生会话 ID | 同一任务续聊使用本任务历史；新任务创建新会话；子任务获得新 ID，通过受控摘要交接上下文 |
| 运行目录 | 账号私有 `ai-runtime/tasks/<taskId>/`，按匿名/显式 Key 模式继续隔离 | 不使用可写链接共享其他任务状态，不导入机器账号凭据；路径来自程序创建的任务记录，不能来自模型输出 |
| `TaskRun` | 输入版本、上下文清单、人设/规则版本、工具调用、预算、取消状态 | 旧运行不能覆盖新运行；恢复先核对范围、规则和凭据目标，不按 PID 或界面选择猜测归属 |
| `ReplyBatch` | 固定任务、目标、计划版本、逐气泡回执和授权快照 | 已确认送达的部分不重发；结果未知的部分须先核对，不能通过“重启任务”绕过 |

HTTP 模型按任务历史显式组装消息，不借用另一个任务的会话。OpenCode 若支持显式会话续接，须先核实当前运行时契约，将原生会话 ID 映射到任务并校验归属；不支持时使用任务私有目录和完整受控历史重建，不通过改用共享目录模拟续聊。换供应方、模型或认证模式时创建新的会话代次，旧代次保留可追溯记录，不盲目续接不兼容状态。

现有账号消费租约继续保证 GUI/CLI 只有一个消息消费者；另加账号内任务认领和版本比较，防止同一任务被多个入口同时执行。任务租约只决定是否可消费任务，不授予结束 QQ 或其他进程的权力。取消仅中止本任务创建并持有所有权的推理/工具工作，已送达消息和外部已完成动作保留回执。

重启后，缺少确定终态的运行记为中断或结果未知，不按时间猜测成功。只读步骤可以在预算和用户设置允许时重新获取；外部写步骤先核对既有回执。任务会话和目录有可配置的保留期、数量/体积限额及明确清理入口；仅清理经作用域和所有权验证的本任务资源，未解决的送达记录不得因普通清理丢失。

## 上下文按权限装配

`ContextEnvelope` 是程序生成的输入快照，包含固定作用域、`inputRevision`、本次输入事件 ID、构建时间、使用的人设/策略版本、来源清单和预算。模型可以使用其中数据，不能自行扩大来源或修改作用域。

| 来源 | 第一版允许装配的内容 | 排除和校验 |
| --- | --- | --- |
| 当前会话 | 授权范围内最近消息、引用关系、发送者/群语境、文字与已识别原生表情、我方已送达内容 | 不重复加入本次来信；不跨账号或跨目标搜索；未知来源不当作事实 |
| 当前任务 | 用户目标、补充指令、任务已完成步骤、工具结果、剩余预算、待确认动作 | 隔离其他任务原始对话；可共享的任务摘要也需同范围权限和来源标记 |
| 人设与关系 | 账号默认人设、联系人/群偏好、任务专用表达要求、明确授权的长期记忆 | 人设不授予工具权限；关系偏好不等于真实身份或经历；敏感推断不自动写入记忆 |
| 文件与检索 | 用户选定的文件、获准群文件、当前账号内获准检索到的片段和引用 | 文件大小/类型、账号根和目标权限校验；不读取任意本地目录、其他会话、密钥或 auth 数据 |
| 操作环境 | 程序确认的时间/时区、固定目标、任务状态、用户明确选择的项目或资料 | 界面焦点不能改变后台任务身份；不扫描其他应用、桌面或环境变量收集上下文 |

外来消息、文件和检索内容作为不可信数据装入，不能覆盖系统规则、授权范围、工具参数白名单或任务身份。每条事实保留来源和观察时间，缺少信息时表达不确定，不把模型补全写成记忆。上下文/token、文件片段数量和工具返回体都有有限且可配置的预算；压缩后的摘要保留范围、来源和版本，不把全文悄悄转移到其他任务。

### 新来信与过时结果

每个会话维护输入版本，每次来信、人工接管、撤销规则或任务指令更新都会使有关运行失效。生成开始时捕获版本；计划落库、预览批准和每个气泡发送前再次核对。新来信到达时，旧结果标为 `superseded`，不能继续自动发送；可以在可配置的短聚合窗口内把同一会话的新消息合并到新运行，避免对每个字都重新推理。

若已有部分气泡送达，则停止未发送部分，记录为部分完成且已过时；新运行读取真实已发送内容与新来信，不能重发旧前缀。用户仍可查看旧草稿，但若要发送必须重新审阅当前上下文和具体内容；不能只改版本号后沿用旧批准。其他账号、目标和无关联任务不因此取消。

### 群聊成员、说话对象与来源

群成员稳定键使用 `accountUin + groupId + memberUin`，并处于当前机器账号数据根之下。昵称和群名片只用于展示及别名历史；同名不合并，改名不新建成员，不能按字符串昵称匹配到另一人。成员身份优先来自当前账号收到并通过身份校验的协议事件；缺少稳定 ID 或来源矛盾时保留未知，不从昵称猜出 QQ 号。

每条上下文事件至少保留 `accountUin`、`groupId`、`memberUin`、协议 `sender`、`self_id`、`mentions`、`replyToMessageId`、`originalMessageId`、事件时间和原始段引用。既保留谁发出当前消息，也保留被提及成员、被引用消息的作者以及发话对象；`at all` 与具体成员引用分别表示。查询被引用原文须仍在同账号、同群且已获准范围内，找不到时明确标记引用未解析。

| 来源或角色 | 程序保留的信息 | 模型可使用的语义 |
| --- | --- | --- |
| 当前说话者 | 稳定成员键、该次显示名、原始消息 ID 与时间 | 区分本轮是谁发话，不把同名者合并 |
| 明确发话对象 | 已验证的提及、引用目标、任务参与者、程序判定的对话指向及其依据 | 判断是在问助手、回复另一成员还是一般群聊；歧义时不冒认对方在对助手说话 |
| 被引用的第三人 | 引用消息 ID、原作者稳定键、原文出处、解析状态 | 当前说话者的补充与第三人的原话分别装配，不能把被引用内容归给当前说话者 |
| 转述或合并转发 | 直接发送者、转发节点/转述声明、节点声称的作者、来源可信度 | 转发中的作者字段只是有来源的声明，不能据此认证现实身份；被转述的指令不变成当前任务授权 |
| 我方及已送达消息 | 本账号 `self_id`、真实发送回执、被回复的成员/消息与任务 | 不触发自回复；准确知道先前已经向谁回复了什么，不将草稿或排队内容当作已发送 |

人设覆盖、关系记忆和任务状态区分群与成员。某成员在某群的偏好保存在该群成员作用域，不能因 QQ 号相同就把私聊内容、其他群的关系或别的任务历史带进当前群；跨范围使用需要明确授权和来源标记。群任务可以包含多个已确定的参与者，参与者的身份与发言分别保留，但不因此共享其他群或其他任务的 AI 会话；必要交接只传获准、带来源与版本的摘要。

回复计划额外绑定程序确定的 `addressedMemberKeys` 和可选的同群来源消息引用；它们是可信信封字段，不允许模型借修改成员/群 ID 改变接收范围。需要引用或提及时，程序只能从已验证的当前群事件装配对应定位信息，不接受模型随意生成 CQ 码、全体提及或第三人 ID。首批正文段仍只有 `text`/`face`；实际引用定位的协议适配须随对应交付明确验证，不能用显示名文本假装协议已引用。

同群出现新发话者或新的引用关系时，新运行重新计算“谁在对谁说话”，不能把旧任务原来对成员甲的回复直接改成发给成员乙。原计划成员和引用保持不可变；过时结果按输入版本失效。第一版以同群输入版本作为保守边界；若后续支持群内并行话题，须先验证来源消息/参与者确定的线程隔离，不能仅按昵称或模型猜测自动分线。

## 人设与自然短句

人设分为账号默认、联系人/群覆盖和任务覆盖；优先级为安全与权限规则、用户当前明确任务、联系人/群覆盖、账号默认。任务覆盖只能收窄工具权限，不能扩大。保存的字段至少包含表达偏好、称呼/关系边界、应避免的话术和版本；允许清空覆盖并返回继承值，不把空值和未传混淆。

提示词强调先回应对方具体内容，少用客服式开场、无必要的长解释、固定结尾和过度热情；日常偏好短句，需要说明时完整表达。允许只发一句、只发一个已验证 QQ 原生表情、连发多条，或在一句中插入原生表情；情境不合适时不发。情绪与关系由授权上下文支持，不捏造熟悉程度、现实经历或已经执行的动作；被问及身份或能力时如实说明。

Unicode emoji 限制作用于新生成的助手输出，不改写原始用户消息、引用证据和历史记录。输出校验覆盖常见组合序列、旗帜、键帽等，避免只检查单个码点；普通汉字、标点和数学符号不能被误删。违反输出策略的计划进入可解释的修订/审核状态，不在发送前静默删字后假装用户已批准。

## 结构化 ReplyPlan 与 QQ 原生表情

程序持有完整可信的 `ReplyPlan`；模型只提交受限的气泡内容候选。以下是建议的领域形状，字段和接口尚未实现：

```ts
type ReplySegment =
  | { type: 'text'; text: string }
  | { type: 'face'; faceKey: string };

interface ReplyBubble {
  id: string;
  segments: ReplySegment[];
}

interface ReplyPlan {
  schemaVersion: 1;
  taskId: string;
  accountUin: string;
  targetType: 'private' | 'group';
  targetId: string;
  inputRevision: number;
  personaRevision: number;
  policyRevision: number;
  addressedMemberKeys?: string[];
  replyToMessageId?: string;
  bubbles: ReplyBubble[];
}
```

`taskId`、账号、目标、版本、成员/引用信封和气泡 ID 由程序赋值或核验，不能采纳模型随意指定的账号/目标/成员。每个 `ReplyBubble` 对应一次 QQ 消息调用；一个气泡里的多个 `text`/`face` 段保持原顺序整体发送，不按组件拆成多条。文本内换行可以属于同一气泡，气泡边界也不等同于句号或网络流式 chunk。

| 可选形态 | 计划中的表示 | 验证结果 |
| --- | --- | --- |
| 纯文字 | 一个或多个气泡，各含 `text` 段 | 不追加表情，不强制拆句；简短回复也可以只有一条 |
| 单独原生表情 | 一个气泡只含已验证的 `face` 段 | 合法，不要求额外补文字；是否适合由语境、人设和用户策略决定 |
| 同一气泡混合 | 一个气泡按顺序包含 `text`、`face` 等多个允许段 | 整个消息链一次发送，不能因为遇到 `face` 破坏原气泡 |
| 多个不同形态气泡 | `bubbles` 中按明确顺序排列上述任意形态 | 按计划和节流投递，不把这种组合规定为每次回复的固定模板 |

`faceKey` 来自程序提供的小型、版本化的可用目录。程序负责将其解析为已验证的协议 `face.data.id`，并校验目录来源、协议版本、停用状态与目标能力；模型不能自由发明数值 ID、CQ 码或未经注册的名称。目录可由可信协议资料与受控夹具验证维护，不能根据模型记忆或单条社区帖子宣称所有 QQ 客户端均兼容。

不支持或映射未知的原生表情不能转成 Unicode emoji，也不能当作有效 `face` 发送。混合气泡可根据明确的降级策略保留可理解文字，并使审核内容与最终内容一致；只有表情的气泡无法验证时进入审核/提示，不发送空消息、不偷偷补上一句与原意无关的文字。纯文字回退仍保留原先纯文字发送能力。

接收侧保留原始消息段，并为模型装配已验证的文字描述与引用。预览侧使用确认的资源或明确文字标签；资源缺失不冒充已经成功显示原生图形。第一版只有基础 `face`，商城 `mface`、图片表情和自定义资源保持不同类型与授权边界。

### 外部资料与采用边界

[NapCat 消息格式文档](https://napneko.github.io/develop/msg) 列出 `text`、基础 QQ `face` 的收发支持，并将基础 `face` 与商城 `mface` 分开；`face` 通过 `type` 与 `data.id` 表示。由此可采用显式消息段适配，但文档本身不能证明任意名称与编号的完整对应表，也不能替代本项目所用版本的夹具及原生显示验证。

[AstrBot issue #10047](https://github.com/AstrBotDevs/AstrBot/issues/10047) 报告了分段回复逐组件发送导致行内文字和 `Face` 被意外拆开的情况。可借鉴的是保留原消息链分组这一边界；这不是禁止单独表情。模型或用户明确选择的独立表情气泡应允许，错误的是发送器擅自改变气泡结构。该 issue 只作为失效场景和回归输入，不宣称已经核验 AstrBot 全部实现、修复合入或其运行效果。

## 批次发送、节奏与回执

自动回复与已批准草稿统一调用领域发送服务。服务绑定任务创建时的账号数据库与 OneBot 客户端，不使用发送时的全局选择。发送前读取当前规则、目标身份、任务/input 版本、授权的计划散列与取消状态；等待节流期间发生撤权或新来信时也要停止。

| 对象 | 有限且可配置的约束 | 语义 |
| --- | --- | --- |
| 回复计划 | 气泡数、每气泡文本长度/段数、总字节数 | 上限不是推荐条数，不补齐气泡；超限不静默截断关键内容 |
| 发送节奏 | 账号总速率、会话队列、气泡间隔、待处理任务数量 | 同会话整批串行，不与另一回复交错；冷却针对逻辑回复，不对每个段重复计费或重新触发 AI |
| 模型与工具 | 任务 token、调用数、步骤数、总时长、并发只读数 | 超出预算暂停并说明，不能无限重试或为补格式隐式连续调用模型 |
| 历史与目录 | 上下文预算、任务/会话保留数量与体积、终态留存期 | 已授权数据最小化装配；未解决的外部动作回执优先保留 |

发送前事务性保存批次及气泡计划，逐项状态为 `pending`、`sending`、`sent`、`failed`、`delivery_unknown`、`cancelled` 或 `superseded`。成功回执保存平台消息 ID、时间、任务/气泡 ID 与最终发送内容；本地消息展示和推送依据确认结果，不把排队或模型生成成功写成已发送。

某气泡失败后立即停止后续气泡。明确未受理的失败可以在用户或规则允许的范围内重试该项；网络断开/超时可能已经送达，应记为 `delivery_unknown`，先核对平台消息或由用户确认，不能重发整个批次。发送后进程崩溃、尚未保存回执的窗口同样属于未知，不能宣称实现跨 QQ 与 SQLite 的绝对一次发送。

批准绑定具体计划版本、输入版本和内容散列，重试只续接允许重试的未发送项；已送达前缀永远保留。原有单文本草稿可作为一个文本气泡迁移，成功后再完成草稿；部分成功时保留剩余部分和回执，不删除整份草稿。事件去重采用账号、会话类型、来源事件 ID、任务和气泡序号；合法的相同短句不按内容删除。

## 首批智能体小场景与权限

智能体第一版是受限的“读取资料、形成计划、生成可审核结果”，不是开放式替用户操作整台电脑。所有工具请求先由程序把任务作用域、权限、路径和预算与模型建议对照；工具结果带来源，不能反过来授予新权限。OpenCode 当前非交互工具限制继续有效，不为了接入智能体把通配权限改成自动放行。

| 小场景 | 首批工具范围 | 授权与交付结果 |
| --- | --- | --- |
| 回答当前会话中的既有事项 | 搜索同账号且已获准的当前会话消息，读取引用附近上下文 | 只读搜索，输出带来源的候选回复；不扩到其他好友或群 |
| 群文件查找与内容整理 | 当前已授权群的文件目录、显式选定文件的受限下载/提取、摘要 | 明确文件范围和大小；生成结论/引用和草稿，下载不扩大到任意 URL 或磁盘路径 |
| 一次任务的待办整理 | 当前任务授权材料提取事项；写入任务自己的本地待办记录 | 本地创建/更新由用户任务明确授权，记录变更；不冒充已同步日历或发送给群成员 |
| 根据检索或工具结果准备回复 | 读取本任务工具结果，生成并预览 `ReplyPlan` | 只有已授权自动回复规则或用户批准具体计划才进入发送器；额外目标和额外渠道需单独授权 |

工具声明区分只读、任务内本地写、QQ 发送和其他外部写。已授权动作不逐气泡重复确认；超出目标、数据源或副作用范围时暂停并展示具体计划。不可通过改写任务人设、调用一个通用“工具执行”入口或复制其他任务会话绕过这些限制。当前任务的授权不自动变成下一任务的永久授权。

## 五阶段交付与验收

以下各阶段当前均为待实现。应按阶段交付源码、生成契约、中文记录和真实证据，不以本文替代实现，也不因为阶段通过宣布整个增长方向完成。代码增量归入 `services/ai/`、`services/protocol/messaging/`、`services/workflows/` 和 `services/storage/` 相应子目录；接口变更统一更新 GUI/CLI/MCP 适配与生成契约。

| 阶段 | 可使用的交付物 | 可验收条件 |
| --- | --- | --- |
| 1. 人设和上下文真实消费 | 账号/联系人/群成员/任务人设继承与编辑、统一回复构造器、来源明确的上下文快照 | 保存后重读及最终模型请求均体现所选人设；所有生成入口一致；本轮来信不重复；跨账号/目标数据不可装配；群成员同名不合并、改名不丢失身份、引用第三人不串作者；新发话者或引用关系变化使旧候选失效并重新确定说话对象；私聊不隐式带入群；不编造身份、不生成 Unicode emoji 的夹具回归通过 |
| 2. 独立任务会话与恢复 | `Task`/`TaskSession`/`TaskRun`、固定作用域、群任务参与者、取消和中断恢复、预算及有界目录 | 同账号同联系人两任务的历史/运行目录不串用；同群多参与者身份独立，跨群/跨任务会话不串用；同任务续聊可恢复；新输入与旧结果竞态不会覆盖；GUI/CLI 认领互斥；取消仅回收本任务自有子进程；跨账号、陈旧状态、换模型和匿名/Key 模式切换有回归 |
| 3. ReplyPlan 与原生 face | 有类型的气泡与消息段、版本化 face 映射、入站识别、逐气泡预览、文本兼容 | 纯文字、独立 face、同气泡混合、多气泡均有夹具；纯 face 输入不被当空消息；未知 face 不乱映射；组件顺序和气泡边界不变；超过可配置容量被准确处理；预览与最终计划一致 |
| 4. 批次投递与回执 | 统一发送器、会话串行与账号节流、持久回执、剩余草稿与受控续接 | 模拟协议覆盖部分成功、超时未知、进程中断、撤权、新来信、重复事件和重复批准；已发前缀不重发；真实 Tauri 在隔离夹具下显示正确结果；实际 QQ 发送只在获得明确授权后另行验证 |
| 5. 小范围工具任务 | 上述只读搜索/文件整理/任务待办与候选回复、可见计划、权限和预算检查 | 一个任务多步完成并给来源；工具不能改账号/目标、跨任务读私密历史或越权写入；注入、错误、取消、预算耗尽、恢复都能停止于准确状态；记录实际成功率、人工修改量、误触发与重复发送，作为是否扩大工具范围的证据 |

## 尚未确定与后续证据

首版 face 名称目录、协议/QQ 版本兼容矩阵、任务与上下文默认预算、容量和节奏默认值，需要在实现对应阶段用受控样本确定并记入配置契约。验证气泡形态和身份隔离时使用模拟协议与任务私有夹具；若需要证明 QQ 客户端实际原生表情的外观和送达行为，单独准备明确授权、固定测试目标和逐条回执，不能用接口文档或模拟成功代替。

本方向的成功不以更长 prompt 或更多工具数衡量。优先验证用户是否更少修改回复、是否能自然使用独立表情或短句、任务是否可恢复、上下文是否准确且不串用、是否避免过时与重复发送；在这些证据成立后再增加长期记忆、主动任务或更多外部工具。
