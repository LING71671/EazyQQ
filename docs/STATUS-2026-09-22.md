# EazyQQ 协议端故障 — 现状说明

**日期：2026-09-22**
**范围：NapCat 协议端无法工作，导致无法登录 QQ、无法收发消息**
**说明：本文只陈述已核实的事实。推测部分单独标注，不与事实混写。**

---

## 一、一句话现状

**应用本身可以正常启动、界面正常、本地数据库与大模型均可用；唯一不可用的是协议端（NapCat），因此无法登录 QQ、无法收发消息。**

---

## 二、故障现象（可复现）

1. 启动 NapCat（`napcat/NapCatWinBootMain.exe`）
2. 其 WebUI 端口 **6099 会短暂监听 2~5 秒**，随后消失
3. 每次启动 NapCat，**QQ 进程会崩溃**（Windows 事件日志有记录，见下）
4. `napcat/logs/` 目录始终为空（配置中 `fileLog: true`、级别 `debug`）

复现命令（在 `B:\EazyQQ\napcat` 下）：

```
NapCatWinBootMain.exe "A:\NTQQ\QQ.exe" "B:\EazyQQ\napcat\NapCatWinBootHook.dll"
```

引导器输出固定为：

```

argv[1]:A:/NTQQ/QQ.exe
argv[2]:B:/EazyQQ/napcat/NapCatWinBootHook.dll
Boot Command:"A:/NTQQ/QQ.exe" --enable-logging
[NapCat Backend] Main Process ID:xxxxx
Creating pipe: \\.\pipe\NapCat_xxxxx
[NapCat Backend] Process resumed
Process exited.
```

## 三、直接证据

### 3.1 Windows 应用程序事件日志

```
出错应用程序名称： QQ.exe，版本： 9.9.28.46928，时间戳： 0x6851d1d3
出错模块名称：   QQNT.dll， 版本： 0.0.0.0，时间戳： 0x69c117ce
异常代码： 0x80000003
错误偏移： 0x0000000007776276
Faulting 应用程序路径： A:\NTQQ\QQ.exe
Faulting 模块路径：   A:\NTQQ\versions\9.9.35-52892\QQNT.dll
```

- `0x80000003` = `EXCEPTION_BREAKPOINT`（断点异常）
- 每次启动 NapCat 对应一次该崩溃，实测时间点：
  `15:46 / 16:07 / 16:10 / 16:15 / 16:18 / 16:21 / 16:39`

### 3.2 崩溃地址处的机器码（对 QQNT.dll 的静态检查）

崩溃偏移 `0x7776276` 处是正常指令：

```
07776276  84 44 FF FF FF ...     即 0F 84 44 FF FF FF = JZ rel32
```

**该地址在磁盘上是正常代码，没有断点指令（0xCC）。**
→ 断点是**运行时在内存中写入**的，不是文件里固有的。

### 3.3 最后成功工作的时间

数据库 `messages_log` 记录：

| 时间 | 方向 | 会话 | 内容（截断） |
| :--- | :--- | :--- | :--- |
| 2026-09-21 23:24:55 | **我发出** | 1104661022 | 哈哈还在推进～自动回复群消息在规划，先跑通底层！ |
| 2026-09-22 00:30:48 | 收到 | 1104661022 | 普通群消息 |

**即：协议端最后一次正常工作在 2026-09-21 23:24 ~ 09-22 00:31 之间。**

## 五、已排除的原因（每项都做过对照实验）

| # | 假设 | 实验 | 结果 |
| :--- | :--- | :--- | :--- |
| 1 | 用户自己的 QQ 在运行导致进程冲突 | 关掉 QQ（0 进程）后重试 | **排除**，照样崩 |
| 2 | Windhawk 全局注入 | 退出 Windhawk（0 进程）后重试 | **排除**，照样崩 |
| 3 | 执行沙箱环境 | 在沙箱外执行 | **排除**，照样崩 |
| 4 | `o3HookMode: 1`（非默认值） | 改为默认 `0` 后重试 | **排除**，照样崩 |
| 5 | `packetBackend` 偏移补丁出错 | 改为 `disable` 后重试 | **排除**，照样崩 |
| 6 | LiteLoaderQQNT 残留 | 全盘搜索 + 检查 `package.json` 的 `main` 为标准路径 | **排除**，无残留 |
| 7 | NapCat 偏移表与 QQNT.dll 不匹配 | 按 PE 节表换算核对：`send 0xC361DF` 处为 `48 89 CA F3 0F 5C`、`recv 0x246F3A1` 处为 `57 53 48 83 EC 20`，**均为合法 x64 函数序言** | **排除**，偏移匹配 |
| 8 | QQ 版本不受 NapCat 支持 | 版本表含 `9.9.35-52892` | **排除**，声称支持 |
| 9 | 混装（4.9.81 hook + 4.18.28 JS） | 恢复为文件层面一致的 4.9.81 | **排除**，仍崩（但混装本身是真实缺陷） |
| 10 | 配置差异 | 对比升级前后备份：仅 `napcat.json` 的 `fileLog` 由 `false` 变 `true` | **排除** |

## 六、尚未查明

1. **为什么 QQ 会在 `QQNT.dll` 中触发断点异常。**
2. **为什么回退到文件层面一致的 4.9.81 仍不能恢复**（说明还存在某个未识别的变量）。

### 需要修正的两个既有说法

- **"以前完全正常"不准确。** 旧版 4.9.81 的日志（应用收集于账号目录 `napcat_logs/`）显示它在
  **8 分钟内被重启十余次**（08:39~08:47），且 08:47 两条日志显示 WebUI 分别起在 **6099 和 6100**
  （多实例抢端口）。**旧版也不稳定，只是能走到"WebUI 就绪"；新版 4.18.28 直接让 QQ 崩溃。**
- **"NapCat 从未写日志"的原因是配置。** 升级前 `napcat.json` 的 `fileLog` 为 `false`，
  因此旧版从不写 `napcat/logs/`；其日志一直靠应用收集控制台输出。

### 当前最可能的方向（**属推测，未经证实**）

崩溃形态（QQNT.dll 内、断点异常、崩溃地址在磁盘上正常）与 NapCat 已知问题族
"**已触发 QQ 文件校验退出函数**"（NapCat issue #798 / #999）特征一致，
即 **QQ 的完整性校验拒绝了 NapCat 的注入**。

若成立，则属于 **NapCat 与 QQ 构建之间的兼容问题，不在本应用代码可修范围内**。

## 九、给接手者的建议

1. **优先验证"QQ 完整性校验拒绝注入"这一假设**——可用 NapCat 官方 OneKey
   （`NapCat.Shell.Windows.OneKey.zip`，1.0 MB，会自动下载配套 QQ）在**隔离目录**中验证，
   不需要改动现有 QQ 安装。
2. **向 NapCat 反馈**：本文第三节的崩溃信息（异常码、出错模块、偏移、QQ 版本、NapCat 版本）
   已足够构成一份有效的 issue。
3. **不建议继续依赖用户的 QQ 安装**：这是本项目反复出问题的结构性原因
   （版本被动升级、路径非标准、可能被其他插件污染）。
   长期方案见 `ISSUE.md` 中"解决方向：私有 QQ 环境"一节。
4. **注意排查方法**：
   - 采样间隔必须短于被测事件的持续时间（本次故障的窗口仅 2~5 秒，5 秒采样会系统性错过）；
   - 本环境的删除走回收站机制，对大量小文件极慢，长路径会失败。
